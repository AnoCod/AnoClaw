# GitHub 协作开发规范

> 适用对象：AnoClaw 维护者、贡献者和执行开发任务的 AI Agent。
> 规范入口：`AGENTS.md` 保存必须遵守的硬规则；本文解释完整流程和仓库配置基线。发生冲突时，以 `AGENTS.md` 和用户在当前任务中的明确指令为准。

## 1. 目标与事实来源

AnoClaw 使用 GitHub 保存可审查、可追溯的协作记录，而不是把聊天记录或本地笔记当作项目事实。

| 内容 | 权威位置 | 说明 |
|---|---|---|
| 代码和稳定文档 | Git 提交及默认分支 | 本地文件必须通过提交进入远端 |
| 需求、缺陷、技术债 | GitHub Issue | 记录背景、范围、验收标准和风险 |
| 方案讨论和代码审查 | Pull Request | 记录实现选择、验证证据和审查结论 |
| 自动验证 | GitHub Actions 与本地验证记录 | CI 是门禁，本地验证补充平台无法覆盖的桌面测试 |
| 版本交付 | Git tag 与 GitHub Release | Release 必须可追溯到默认分支上的提交 |
| 长期工程规则 | `AGENTS.md` 与 `docs/` | 不把规则散落在聊天、Issue 评论或私人笔记里 |

上游仓库为 `AnoCod/AnoClaw`，默认集成分支为 `main`。操作 fork 时必须同时确认上游仓库、推送仓库和 PR 目标，不能只根据本地 `origin` 猜测。

## 2. GitHub 插件、本地 Git 与 `gh` 的分工

1. GitHub 插件优先用于读取和操作仓库元数据：Issue、PR、评论、审查、标签、反应和工作流运行状态。
2. 本地 `git` 负责源文件、差异、分支、暂存、提交和推送。这能保证本地验证过的内容与远端提交完全一致。
3. `gh` 只补齐插件覆盖不足的场景，例如读取 Actions 详细日志、定位当前分支对应的 PR，或检查仓库设置。
4. 已有本地检出时，不通过 GitHub Contents API 同时修改同一分支；否则本地和远端会形成两个写入源。
5. 执行远端写操作前，明确复核 `owner/repo`、Issue 或 PR 编号、基准分支、来源分支和具体动作。
6. 读取远端上下文可以作为正常诊断步骤。创建、更新、关闭、合并、发布、改保护规则或删除远端对象，必须属于用户授权的任务；合并、关闭、发布、删改和仓库设置变更需要明确批准。

## 3. 工作项分级

| 等级 | 典型内容 | Issue 要求 | PR 要求 | 验证要求 |
|---|---|---|---|---|
| 轻量 | 拼写、纯注释、无行为变化的小文档修正 | 可省略 | 合入 `main` 仍需 PR | 差异、链接和格式检查 |
| 标准 | 功能、缺陷、重构、测试、依赖或配置变更 | 必须 | 必须 | 聚焦测试加适用构建 |
| 高风险 | 安全、数据格式、会话存储、协议、权限、自动更新、发布流程 | 必须 | 必须，优先独立审查 | 完整测试、构建、回滚方案及人工验证 |
| 紧急 | 已确认的生产阻断或安全事件 | 先建或事后补 Issue | 使用 `hotfix/` PR | 最小修复、必要验证、事后复盘 |

“改动很小”不能用来规避高风险分类。涉及认证、密钥、持久化、升级或发布的少量代码仍属于高风险。

## 4. Issue 规则

标准和高风险工作在编码前创建或确认 Issue。Issue 至少包含：

- 可复现或可验证的背景，而不是只写解决方案名称；
- 明确的目标、范围内和范围外事项；
- 可逐项验证的验收标准；
- 依赖、兼容性、数据和安全风险；
- 计划执行的测试或验证；
- 已知阻塞项和负责人。

建议标签体系：

- 类型：`type:bug`、`type:feature`、`type:docs`、`type:refactor`、`type:test`、`type:chore`、`type:security`；
- 优先级：`priority:P0` 至 `priority:P3`；
- 状态：`status:needs-triage`、`status:ready`、`status:blocked`；
- 领域：`area:server`、`area:frontend`、`area:electron`、`area:plugin`、`area:coordination`、`area:build`、`area:docs`。

标签表达分类，不代替 Issue 正文。安全漏洞、密钥泄漏和包含私人数据的问题不得创建公开 Issue，应使用 GitHub Security 私密渠道。

## 5. 分支规则

开始工作前先获取远端状态并确认基准分支。每个分支只承载一个可解释的逻辑目标。

| 作者或用途 | 格式 | 示例 |
|---|---|---|
| Codex | `codex/<issue>-<slug>` | `codex/142-session-recovery` |
| 功能 | `feat/<issue>-<slug>` | `feat/142-session-recovery` |
| 缺陷 | `fix/<issue>-<slug>` | `fix/208-ws-reconnect` |
| 文档 | `docs/<issue>-<slug>` | `docs/310-plugin-api` |
| 其他工程工作 | `refactor/`、`test/`、`chore/` | `chore/88-update-tooling` |
| 紧急修复 | `hotfix/<issue>-<slug>` | `hotfix/401-key-leak` |

规则：

- 禁止在 `main` 上直接开发或常规推送；
- 分支名使用小写 ASCII、数字和短横线，不放用户名、密钥、客户名或私人信息；
- Issue-less 分支仅限已确认的轻量维护，可省略编号；
- 分支过期或目标改变时新建分支，不把无关工作继续堆入旧分支；
- 不通过强推、重写共享历史或删除引用来解决普通同步问题；
- 更新基准分支时遵守 `AGENTS.md` 的历史安全规则。任何 rebase 或 squash 历史改写都必须先确认范围、保留备份并取得所需批准。

## 6. 提交规则

提交应当原子化：能独立说明意图，且不会夹带无关文件。主题使用 Conventional Commits：

```text
<type>(<scope>): <imperative summary>
```

常用类型为 `feat`、`fix`、`docs`、`refactor`、`test`、`build`、`ci`、`chore`、`perf` 和 `revert`。示例：

```text
feat(coordination): add durable task leases
fix(session): preserve history after restart
docs(github): define collaboration workflow
```

- 主题简洁、使用祈使语气，正文解释“为什么”及不明显的权衡；
- 破坏性变更用 `!` 和 `BREAKING CHANGE:` 明确标记；
- 仅暂存任务范围内文件，禁止默认把混合工作区全部加入；
- 不提交构建缓存、运行数据、安装产物、私有配置和密钥；
- 不声称执行过实际未运行的测试；
- AI 生成提交必须由执行者检查完整差异和验证结果，AI 身份不能替代责任人。

## 7. 验证矩阵

| 改动范围 | 最低验证 |
|---|---|
| 纯 Markdown / Issue 模板 | 检查差异、链接、JSON/YAML 解析和 GitHub 模板结构 |
| 前端 TypeScript / CSS | 聚焦测试、`npm run build:frontend`；跨层时升级为完整构建 |
| 服务端或共享 TypeScript | 聚焦测试、`npm run build`；跨层时升级为完整构建 |
| 跨层行为或公共协议 | `npm test`、`npm run build:all` 和相关运行验证 |
| 任意应用代码变更 | 按项目 `anoclaw-test-build` 技能执行干净重建、打包及安装版验证 |
| 安装、更新或发布 | 使用项目打包技能，并对产物执行启动和关键路径冒烟测试 |

若某项验证因环境原因无法执行，应在 PR 中写清命令、阻塞原因、剩余风险和由谁补验。失败检查不得被模糊写成“基本通过”，也不能靠重复运行来掩盖可复现失败。

## 8. Pull Request 生命周期

### 8.1 创建

- 有助于协作时尽早创建 Draft PR；不稳定的草稿不能标记为可审查；
- PR 标题使用可成为最终提交的 Conventional Commit 主题；
- 使用 `Closes #123`、`Fixes #123` 或明确的关联方式连接 Issue；
- PR 描述随范围变化同步更新，不能只保留最初的过时计划；
- 大改动按可验证边界拆分。若不能拆分，在描述中解释原因和审查顺序。

### 8.2 请求审查前

作者必须完成：

1. 查看从目标基准到当前 HEAD 的完整差异，而不只看最后一次提交；
2. 删除调试输出、临时文件、秘密和无关生成物；
3. 运行范围对应的验证并记录真实结果；
4. 更新相关文档、类型、测试和迁移说明；
5. 标注 UI 截图、协议变化、数据兼容性、风险与回滚；
6. 确认无未解释的失败检查和冲突。

### 8.3 审查标准

审查按以下顺序关注：

1. 正确性、数据安全、权限边界和兼容性；
2. 回归风险、并发、错误处理和恢复路径；
3. 测试是否覆盖行为而不是只覆盖实现；
4. 架构边界、插件优先原则和可维护性；
5. 可读性、命名和样式。

必须处理所有要求修改的意见。作者可以用证据解释不采纳，但不能静默忽略。讨论在修复或达成明确结论后再标记解决；另一位审查者存在时，优先由审查者确认解决。

### 8.4 合并

满足以下条件才可合并：

- 验收标准完成，PR 描述与实际差异一致；
- 必需检查通过，未执行项已有明确批准和风险说明；
- 没有冲突、未解决审查线程或待处理的 required change；
- 有独立维护者时至少一人批准；只有单一维护者时，留下自审记录并通过所有可用门禁；
- 发布、迁移和回滚要求已经完成。

普通 PR 默认 squash merge，并使用合格的 PR 标题生成最终提交。只有当多个提交本身构成有价值、可独立回滚的历史时才保留提交。合并确认后删除来源分支。

## 9. GitHub Actions 与依赖自动化

新增工作流时必须遵守：

- 顶层或 job 级 `permissions` 默认只读，按单个 job 最小化提升；
- 第三方 Action 固定到经过审查的完整提交 SHA，并用注释记录对应版本；
- fork PR 中的不可信代码不能获得写 token 或仓库 secrets；
- 避免 `pull_request_target` 执行 PR 分支代码；确需使用时必须单独安全审查；
- 日志、缓存和 artifact 不包含密钥、用户数据、私有配置或完整敏感路径；
- CI 脚本应能在本地复现，不能把关键验证只藏在网页配置中；
- Dependabot 或其他机器人更新应保持单一依赖主题，通过相同测试和审查门禁，不自动绕过合并规则。

建议分阶段建立门禁：先添加稳定的构建和测试工作流，观察可靠性，再将其设为 `main` 的 required checks。未稳定的偶发失败检查应先修复并用 Issue 跟踪，不能长期要求维护者反复点击重跑。

## 10. 发布规范

- 发布从 `main` 上已验证的提交产生，不从个人工作区或未合并分支手工上传；
- 版本遵循 SemVer，tag 使用 `v<major>.<minor>.<patch>`；
- 发布 PR 统一版本号、变更说明、升级说明和必要的锁文件；
- GitHub Release 说明按用户可见功能、修复、破坏性变化、升级步骤和已知问题组织；
- Windows 安装包和便携包必须由项目打包流程生成，并完成安装版冒烟验证；
- 记录产物校验值。发布后不得静默替换同名资产；需要修复时发布新版本；
- 只有明确授权的维护者可以创建 tag、发布 Release 或修改已有发布。

## 11. 公开仓库安全规则

本仓库是公开仓库，以下内容不得进入 GitHub 的任何公开表面：

- LLM、GitHub、MCP 或其他服务的 API key、token、cookie、认证头；
- `config/settings.yaml` 等本地私有配置、加密密钥和认证文件；
- 用户会话、memory、workspace、日志、数据库和插件私有数据；
- 未脱敏的本机用户名、绝对路径、IP、客户名、提示词和业务数据；
- 带秘密的终端输出、截图、Actions 日志或 artifact。

发现泄漏时先撤销或轮换凭据，再评估清理 GitHub 内容与历史。仅删除文件、Issue、评论或提交不能使已经暴露的凭据重新安全。漏洞通过仓库 Security 页面私密报告，不在公开 Issue 中提供利用细节。

## 12. 仓库设置基线

仓库管理员应在 GitHub Rulesets / Branch protection 中逐步落实：

- `main` 禁止删除和强推，常规变更必须通过 PR；
- 要求解决所有对话；CI 稳定后要求对应 build/test 状态检查；
- 有多人维护时要求至少一名独立批准，并在新提交后撤销过期批准；
- 默认使用 squash merge；自动删除已合并分支；
- Actions 默认 token 权限设为只读，工作流按需单独提权；
- 开启私密漏洞报告和依赖安全告警；
- 自动合并只在 required checks、审查和分支规则都稳定后启用；
- 管理员绕过只用于记录清晰的紧急事件，事后补 Issue、测试和复盘。

规则文件不能证明网页端设置已经启用。修改设置后应把实际值与本节逐项核对，并在对应 Issue 或 PR 留下完成记录。

## 13. Definition of Done

一个 GitHub 开发任务只有同时满足以下条件才算完成：

- Issue 的验收标准已完成，或轻量任务有清楚的直接需求；
- 实现、测试和文档一致，完整差异已自审；
- 所需验证真实通过，例外和剩余风险已记录；
- 只提交任务范围文件，提交和分支命名符合规范；
- 分支已推送，供审查或合并的工作已创建或更新 PR；
- 审查意见和 CI 状态已处理；
- 合并、发布或仓库设置等高影响动作获得所需授权；
- 最终报告包含提交、分支、验证、Issue/PR 链接和未完成事项。
